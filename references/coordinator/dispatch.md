# Coordinator · dispatch and supervision

Read when issuing, continuing or replacing a lease and while supervising runtimes.

- Before a new assignment run `runtime-plan --sdd <sdd>`: it turns the brief's obligations, `runtime-view` candidates and the active host profile into the exact host calls to make — `idle_continuation` for an eligible runtime, `spawn` with the tier model and isolation arguments only when none qualifies, `wait` on an active lease, `close` for retired runtimes — each with the `runtime-record` to write afterwards. It executes nothing and grants nothing. Record host facts with `runtime-record` (`observe`, `guidance`, `supervision`, `retire`, `close_result`, `spawn_result`, `usage`).
- When the host offers `usage_read`, record its result with `runtime-record` action `usage` (`usage: {operation: "usage_read", input_tokens, output_tokens, total_tokens}`). The controller keeps a `token_ledger` and derives tokens per credit unit; a goal-enabled Operator `dispatch` then returns `goalTokenBudget` (credit units of the grant × calibrated or default tokens per unit) to pass as the host `goal_set` token budget. Prefer the `bounded` Operator profile (efficient tier) for closed mechanical routes; keep the frontier tier for the Coordinator only.
- Operator: `dispatch --agent operator --agent-id <host handle> --worktree-root <repo> --scope-json '[...]' --work-item <text> --soft-deadline 30 --hard-deadline 60 [--packet PCxx] [--guidance-id <runtime_record>] [--operator-profile standard|bounded] [--operator-goal required|unavailable]`. `bounded` needs signed closed-route guidance.
- Architect: `dispatch --agent architect ... --soft-deadline 20 --hard-deadline 40 [--verification-mode standard|bounded-correction|fresh-independent|design-counsel] [--fresh-reason ...] [--prepared-id ...]`. Architect product dispatch requires a READY Operator self-check handoff.
- `dispatch` and `prepare` mint the role credential inside the controller and return `capabilityFile`. Hand exactly that path to the dispatched runtime as `SDD_LOOP_AGENT_TOKEN_FILE`; never create, choose, read, log or forward role tokens. A prepared Architect keeps its preparation capability when formally dispatched with `--prepared-id`.
- Verification modes: `standard` reuses the latest Architect of this epoch (a different Architect is rejected); `fresh-independent` requires a distinct Architect and one enumerated `--fresh-reason` (`material-contract-or-architecture-change`, `capability-or-authority-incident`, `prior-architect-unavailable-or-timed-out`, `verification-quality-or-anchoring-failure`, `explicit-user-or-sdd-independent-verifier`, `design-counsel-participation`); `bounded-correction` requires `ARCHITECT_VERIFY` and `--correction-finding-id` of an open Finding authored by that same Architect. Metadata for another mode is rejected, and Operator/design-counsel/probe dispatch carries none.
- Parallel final verification: when the SDD's `delivery_plan` declares `final_verification_shards`, dispatch one Architect per shard in `FINAL_VERIFY` with `--verification-shard <id>`; the first may be the round Architect in `standard` mode, each further shard needs a distinct Architect with `--verification-mode fresh-independent --fresh-reason parallel-final-verification-shard`. Shard leases run concurrently (they write no product files), each verifies exactly its shard's acceptance, and `FINAL_VERIFY → SHIP` requires a PASS verdict for every planned shard with no live shard lease (`FINAL_VERIFICATION_SHARD_MISSING`, `FINAL_VERIFICATION_SHARDS_ACTIVE`). Any other concurrent dispatch still fails `ACTIVE_AGENT_LEASE_EXISTS`. Pause and cancel stop all shard leases.
- `bounded` Operator additionally requires `--operator-goal required` (without a `--goal-unavailable-reason`) and no earlier no-progress observation for the same packet or work item.
- Once a runtime has a `runtime-record observe` entry, every non-probe dispatch to it needs `--guidance-id`.
- The first Operator dispatch of a round freezes the worktree baseline; replacements and later packets reuse it (same `--worktree-root`, generated paths may only grow), so predecessor changes stay in every candidate delta. `ROUND_CLOSED` retires it.
- `--resume-checkpoint` accepts only a signed `SAFE_TO_RESUME` checkpoint of the same role, phase and revision whose lease is no longer active.
- When preparation has a concrete latency benefit, `prepare` the eventual Architect for read-only context during Operator work; failure falls back to ordinary startup. Preparation defaults to reading and environment readiness, not a second full acceptance pass. A selected early falsifier needs a route-changing reason and estimated minutes; record its measured run in a `baseline_check` or `packet_check`. Dispatch with `--prepared-id` to reuse reading. Formal verification keeps its own measured evidence.
- Supervise on host events, command timeouts, lease deadlines and declared checkpoints, not short polling. Deadlines are absolute: the brief's `lease_deadlines` lists every live lease with its seconds remaining, and `runtime-plan` waits only until the nearest one. An expired lease appears as `HANDLE_EXPIRED_LEASE:<lease>` (and an uncomputable one as `LEASE_DEADLINE_UNVERIFIABLE:<lease>`): take the existing timeout path (`operator-reconcile` replace or the failure record) instead of waiting. `runtime-plan` lists closes of retired runtimes before any wait, continuation or spawn and reports the rest under `lifecycle`: `RETRY_BLOCKED` after a FAILED, UNKNOWN or UNAVAILABLE close until a later observation changes close availability, control or host status (a repeated observation with the same facts is not a change), `CLOSE_UNAVAILABLE` while the latest observation says this session cannot close, `RELEASE_UNCONFIRMED` for CLOSED without released capacity, and `SPAWN_BLOCKED_BY_LIMIT` after a `spawn_result` LIMIT until a close releases capacity, a spawn succeeds, or you record a new `runtime-record` `capacity` observation (`capacity: {observed_at, available_slots, source}`) with free slots, which permits one attempt; reuse an eligible runtime meanwhile. `capacity` in the plan separates `executing`, `reusable` and `release_unconfirmed` runtimes and reports host slots as `unknown` until observed. Profile availability is protocol support, not proof that this session holds the tool. Entering SHIP or BLOCKED revokes outstanding leases and preparation in the same commit. After SHIP, BLOCKED, CANCELLED or while PAUSED, `runtime-record` still accepts `observe`, `retire` and `close_result` so host resources can be wound down; nothing else changes. Record observations as they are: a runtime that lost control is observed with `controllable: false`, and unknown stop or close facts are `null` rather than guesses; such a runtime is simply not eligible for reuse. A historical Coordinator is recorded as a host resource with `agent_role: "coordinator"` so it can be retired and closed after its recorded descendants are retired; it never becomes a product role, and the current Coordinator is never a runtime-record subject. Use the neutral [host operations](../hosts.md#operations): `direction_update` queues guidance without a turn, `idle_continuation` starts or resumes a turn on an idle agent, `interrupt_turn` stops only the current turn (the agent stays available), `wait` blocks on updates instead of polling, `observe` lists the live tree for `runtime-record observe`, and `close` ends an agent (and descendants where the profile says so). Call names and parameters come from `capabilities` → `features.host.operations`; an unavailable operation is reported, never emulated. None of them mutates Goal state.
- Record host observations of Operator returns with `operator-reconcile --observation-json`:

  ```json
  {
    "observation_id": "OBS-unique",
    "disposition": "continue",
    "worktree_fingerprint": "<current worktree-view fingerprint, or UNBOUND without a baseline>",
    "host": { "runtime_status": "healthy", "writer_stopped": false, "commands_stopped": false, "evidence": "<actual host return>" },
    "unfinished": ["<remaining admitted observable>"],
    "next_action": "<next concrete action>",
    "reason": "<evidenced reason>",
    "no_progress": false
  }
  ```

  `continue` needs a healthy runtime, unfinished work, an unexpired lease and an unchanged source. `replace` needs writer and commands stopped, revokes the lease and records `operator_recovery`; the next Operator lease must pass a recovery readback before any product evidence. `handoff` needs empty `unfinished` and READY self-check evidence. A `no_progress` observation that repeats for the same work, and any replacement after no progress, require `diagnosis` with `dispatch_prompt`, `last_tool_result`, `host_state`, `diff_review`. The same `observation_id` with identical content is idempotent. See [execution](../execution.md).
- Optional before-action guard: when the host exposes a trusted deny-capable hook, its adapter calls `pre-action` for the active lease before each repository action with the real `--action-kind`, `--affected-package` values, `--command-class` and `--dependency-effect`. Operator writes are allowed only inside the lease's modification scope; Architect repository writes, delegation, unknown actions and unapproved high-impact dependency effects are denied. Without such a hook, report `pre-action guard: unavailable`, never claim machine interception, and keep Architect's independent diff check mandatory.
